1. Общие сведения

1.1. Предмет разработки

Программно-аппаратный комплекс: **минималистичная специализированная ОС на ядре Linux** (Linux-appliance), предназначенная для централизованной **бездисковой загрузки** клиентских ПК по сети. Клиенты работают без локального системного диска: ОС, приложения и (опционально) игровые/данные-диски отдаются с сервера.

Сервер **не является** обычным дистрибутивом Linux с графической оболочкой и пакетами «на все случаи». Это **урезанная Live/DOM-система** с собственной оболочкой управления (TUI и/или Web). После загрузки администратор **не видит стандартную консоль Linux**, а попадает в меню продукта.

1.2. Цели проекта

1. Заменить Windows-сервер CCBoot Linux-appliance с сопоставимым сценарием для интернет-кафе, учебных классов, офисов и лабораторий.

2. Обеспечить загрузку 50+ клиентских ПК с одного сервера (целевой ориентир первой очереди).

3. Хранить один «золотой» образ ОС и отдавать его многим клиентам без порчи оригинала (Copy-on-Write / write-back).

4. Дать администратору простой интерфейс: сеть, DHCP, диски, образы, клиенты, статус — без знания Linux.

5. Уложить саму ОС сервера в **100–200 МБ** (Live USB / Disk-on-Module).

1.3. Задачи первой очереди

• Собрать минимальное ядро и rootfs (Buildroot / Yocto / Alpine).

• Поднять DHCP + TFTP + iPXE и iSCSI Target (или NBD).

• Реализовать write-back через ZFS clones или LVM+dm-snapshot.

• Реализовать read-cache в RAM и write-cache на SSD/NVMe.

• Сделать TUI-оболочку (ncurses/dialog) как основной UI.

• Провести нагрузочный тест одновременной загрузки 50+ ПК.

1.4. Вне скоупа первой очереди (явно)

Не блокируют старт, но **не обязательны** в MVP:

• полноценный аналог CCBoot Hybrid (ОС на локальном SSD клиента, с сервера только game-диск);

• графический PXE-меню конструктор «как в CCBoot»;

• облачный личный кабинет / SaaS;

• автоматический PnP «один образ на любое железо» без участия администратора;

• загрузка macOS-клиентов;

• коммерческая система лицензирования.

3. Назначение и сценарии использования

3.1. Назначение

LXBoot — сервер бездисковой загрузки:

• выдаёт IP и параметры PXE (DHCP);

• отдаёт загрузчик (TFTP/HTTP);

• монтирует клиенту системный диск по iSCSI (основной путь) или NBD (запасной);

• изолирует записи клиентов от золотого образа;

• кэширует чтение в RAM и запись на SSD;

• управляется через TUI (и опционально Web).

3.2. Типовые сценарии

1. **Интернет-кафе / клуб:** парк ПК без дисков, один Windows-образ, чистое состояние после reboot, общий game-диск.

2. **Учебный класс:** Linux- или Windows-клиенты, сброс лабораторных изменений.

3. **Офис / тонкие рабочие места:** персональные диски для профилей, золотой образ ОС.

4. **Лаборатория разработки:** несколько образов (Win10, Win11, Debian), выбор по группе или PXE-меню.

4. Архитектура

4.1. Принцип

Клиент:

1. Включает PXE/UEFI Network Boot.

2. Получает DHCP: IP, next-server, имя NBP.

3. Качает iPXE/PXELINUX по TFTP (далее — chainload, опционально HTTP).

4. iPXE подключает iSCSI LUN (системный диск = золотой образ + per-client overlay).

5. Стартует гостевая ОС (Windows или Linux) как с локального диска.

6. Записи идут в write-back на SSD/NVMe сервера, чтение горячих блоков — из RAM-cache.

Сервер — один Linux-appliance:

┌─────────────────────────────────────────────────────────────┐
│                     LXBoot Appliance                         │
│  TUI / Web  →  control-daemon (lxbootd)                      │
│       │                                                      │
│       ├─ dnsmasq или Kea (DHCP) + TFTP + HTTP boot           │
│       ├─ iPXE bundle                                          │
│       ├─ LIO/targetcli (iSCSI)  и/или nbd-server             │
│       ├─ ZFS или LVM+dm-snapshot (образы, клоны, write-back) │
│       ├─ bcache/dm-cache или ZFS ARC+L2ARC (RAM/SSD cache)   │
│       └─ metrics (cpu, ram, nic, disk i/o, client status)    │
│                                                              │
│  Rootfs: Buildroot / Yocto / Alpine, без desktop             │
│  Носитель ОС: USB / DOM, 100–200 МБ                          │
│  Данные: отдельные диски Image / Write-back / SSD-cache      │
└─────────────────────────────────────────────────────────────┘

4.3. Роли дисков сервера

Как в CCBoot, администратор назначает роль диску, а не правит fstab вручную:

РольНазначение
System / DOMСама appliance (USB/DOM), read-only squashfs + overlay

Если Image или Write-back не назначены — TUI обязан это показать как ошибку конфигурации и **не** молча писать на системный DOM.

4.4. Сетевая модель

• Один или несколько Ethernet (1/10/25/40 GbE).

• Поддержка LACP для каналов к клиентской сети.

• Рекомендуется отделять (логически или физически):

- **boot/storage LAN** (DHCP/PXE/iSCSI);

- **uplink** (интернет, если нужен серверу).

• Встроенный DHCP может работать как:

- **authoritative DHCP** всей LAN (другой DHCP должен быть выключен);

- **proxyDHCP / PXE-only** (2-я очередь, для сетей с существующим DHCP).

• Порты (ориентир, аналог CCBoot):

- UDP 67/68 DHCP, UDP 69 TFTP, TCP 3260 iSCSI, TCP/UDP 80/8080 HTTP boot и Web UI, служебный API (например 8001, только localhost или LAN admin).

4.5. Логика write-back и super-client

**Обычный клиент**

• При старте: ZFS clone (или LVM snapshot) от золотого образа → LUN.

• Запись клиента живёт в clone.

• При выключении/перезагрузке по политике группы:

- **Reset** (по умолчанию): clone уничтожается, следующий boot — снова чистый;

- **Keep** (опционально): clone сохраняется (персональная «грязь» системы);

- personal disk при этом не трогается.

**Super Client**

• Админ включает режим на одном ПК.

• Записи идут в выделенный clone, помеченный как «кандидат в золото».

• После выключения: действия «Сохранить в образ» / «Отбросить».

• Сохранение создаёт новый restore point и переключает «текущий» золотой образ.

• Пока Super Client активен, TUI показывает предупреждение: нагрузка выше, массовое обновление game-диска блокируется (когда появится game-диск).

**Restore points**

• Create (автоматически при сохранении Super Client).

• Restore to last.

• Merge to last.

• Merge all (освобождение места; необратимо; только если образ проверен).

5. Функциональные требования

Приоритеты: **M** — must (MVP), **S** — should (сразу после MVP), **C** — could.

5.1. Управление клиентами — M

1. Учёт клиента по MAC (основной ключ).

2. Привязка IP: вручную или из пула DHCP.

3. Имя ПК, заметка, группа.

4. Автообнаружение неизвестных PXE-MAC (появление в «непрописанных»).

5. Группы: разный образ, разная политика write-back, разные дополнительные LUN.

6. Статус: online/offline (по iSCSI session / DHCP lease / last seen).

7. Метрики клиента: примерная скорость чтения/записи, объём write-back, uptime сессии.

8. Действия: включить/выключить Super Client, сбросить write-back, назначить образ, отправить reboot **если** есть клиентский агент (агент — S).

5.2. Управление образами — M

1. Импорт:

- сырой `.img` / `.raw`;

- `.vhd` / `.vhdx` (обязательно для миграции с CCBoot/Hyper-V);

- выгрузка с физического диска, подключённого к серверу (P2V).

2. Загрузка образа **с клиента** по сети (аналог CCBoot Image Upload) — S, в MVP допустим импорт файлом на сервер.

3. Назначение образа группе или конкретному MAC.

4. Write-back на SSD/NVMe, золотой образ на Image-диске.

5. Super Client и слияние в золотой образ.

6. Несколько образов на сервере (Windows и Linux).

7. Монтирование образа на сервере для обслуживания (loop/zvol) — S.

Форматы хранения внутри пула: zvol или dataset+file. Для iSCSI предпочтителен **zvol**.

5.3. Кэширование — M

1. Read cache в RAM: горячие блоки золотого образа (загрузка Windows, DLL, игровые файлы — когда будет game-диск).

2. Write cache / write-back на SSD/NVMe, не на медленном HDD.

3. В TUI задаются размеры RAM-cache на роль диска (как «RAM Cache» в CCBoot).

4. Защита: нельзя отдать под cache больше, чем свободно, с запасом под ОС (минимум 1–2 ГБ RAM серверу).

5. Отображение disk idle / saturation — S.

5.4. DHCP / PXE / iSCSI — M

1. Настройка пула IP, netmask, gateway, DNS, lease time.

2. Резервации IP по MAC.

3. Выбор boot-файла BIOS vs UEFI автоматически (dnsmasq `dhcp-match`).

4. iSCSI: LUN на клиента, CHAP опционально (S), взаимная изоляция LUN.

5. Запрет двум клиентам писать в один и тот же RW clone.

6. Логирование отказов PXE/TFTP/iSCSI в TUI «журнал».

5.5. Оболочка управления (урезанный интерфейс) — M

После boot сервера — **только меню LXBoot**, не bash prompt.

Пункты меню MVP:

1. Сетевые интерфейсы: IP, mask, gateway, DNS, LACP.

2. DHCP: пул, опции, включения/выключения службы.

3. Диски: обнаружение, роль, монтирование, RAM-cache.

4. Образы: список, импорт, образ по умолчанию, restore points.

5. Клиенты: список MAC/IP/статус, группы, Super Client.

6. Статус системы: CPU, RAM, сеть (pps/bps), Disk I/O, число online-клиентов.

7. Журнал событий и ошибок.

8. Служебное: перезапуск служб, reboot/shutdown appliance, смена пароля admin.

9. «Техническая консоль» (root shell) — **скрытый пункт по паролю**, не на первом экране.

Web-интерфейс (S): те же функции, без обязательного JS-фреймворка; API того же `lxbootd`.

5.6. Personal disk и Game disk — S

1. Personal disk: отдельный zvol на клиента, переживает reboot системного образа.

2. Game disk: один read-only (или CoW с редким Super Client) LUN, общий для группы.

3. Несколько LUN на клиента (C:, D: для Windows).

5.7. Отказоустойчивость и масштаб — C / частично S

1. Multi-NIC без LACP: разнесение DHCP и iSCSI — S.

2. LACP — M (настройка в TUI), работоспособность зависит от свитча.

3. Второй сервер + failover/load balance — C (заложить протокол состояния позже).

4. Целевая нагрузка MVP: **50+ одновременных загрузок**, затем устойчивая работа сессии.

6. Нефункциональные требования

6.1. Размер и характер ОС сервера

• Образ appliance ≤ **200 МБ** (цель 100 МБ без iPXE-бандлов и firmware).

• Rootfs: squashfs + tmpfs overlay; данные образов **не** на корневом разделе.

• Работа как Live USB и как установка на DOM/USB.

• Обновление appliance — атомарная смена образа (A/B или replace + reboot), конфиг `/etc/lxboot` сохраняется.

6.2. Производительность

Ориентир на стенде:

• 50 клиентов, одновременный PXE+Windows boot «холодный старт»;

• сеть сервера 10 GbE (минимум для этого теста; 1 GbE — деградация, но система должна работать на меньшем числе клиентов);

• Image на HDD или SSD, write-back на NVMe, RAM ≥ 32 ГБ.

Критерии (первая очередь, уточняются на прототипе):

• 50 DHCP+TFTP выдач без потери PXE;

• iSCSI login всех 50 за разумное окно (фиксируется по результатам этапа 5);

• после массового boot — отсутствие обвального latency iSCSI (watchdog, очередь, drop).

6.3. Надёжность

• Падение TUI не роняет iSCSI.

• Службы под systemd/OpenRC с автоперезапуском.

• Некорректное выключение: ZFS intent log / import; клиенты после рестарта сервера получают новые clone по политике.

• Заполнение write-back диска: запрет новых сессий + авария в TUI, без порчи золотого образа.

6.4. Безопасность

• Пароль администратора TUI.

• Нет открытого SSH по умолчанию (включается из меню).

• iSCSI LUN только для известного IQN/IP/MAC.

• Web UI (когда появится) — HTTPS, пароль, bind на выбранный интерфейс.

• Без «магического» root-login на первом экране.

6.5. Совместимость железа сервера

Ядро: virtio, основные Intel/Realtek/Broadcom NIC, NVMe, AHCI, USB storage, bonding, vlan.

Расширение драйверов — через пересборку Buildroot, не через apt «на живую» (если база Alpine — отдельное решение, но цель та же: закрытый набор).

6.6. Документация

• Руководство администратора (первый запуск, DHCP-конфликт, импорт образа, Super Client).

• Схема сети «выключите DHCP на роутере».

• Описание ролей дисков и расчёта RAM-cache.

7. Требования к аппаратному обеспечению

7.1. Сервер (минимум для разработки)

• CPU x86_64, 4 ядра;

• RAM 16 ГБ;

• 1 GbE;

• USB для appliance;

• любой диск под Image+WB (можно один, роли logical).

7.2. Сервер (рекомендуемый на 50 клиентов)

• CPU 8+ ядер;

• RAM 32–64 ГБ (часть под ARC);

• 10 GbE, желательно 2 порта / LACP;

• NVMe под write-back и L2ARC;

• HDD/SSD большой ёмкости под Image;

• DOM/USB под ОС.

7.3. Клиенты

• PXE 2.x NIC или UEFI HTTP/PXE;

• без обязательного локального диска;

• для Windows-образа — типичные CPU/RAM гостевой ОС.

8. Интерфейсы и данные

8.1. Модель данных (минимум)

Сущности: `nic`, `dhcp_pool`, `disk`, `image`, `restore_point`, `group`, `client`, `session`, `lun_map`, `event_log`.

Клиент: MAC, IP, hostname, group_id, image_id, wb_policy, super_client, personal_zvol, last_seen, rx/tx stats.

8.2. CLI

Пример: `lxboot client list`, `lxboot image import FILE`, `lxboot client super MAC on`, `lxboot status`.

TUI — обёртка над тем же CLI/демоном.

8.3. Журналирование

journald или файлы `/var/log/lxboot/`. События: PXE, iSCSI login/logout, super-client, import, disk full, service restart.

9. Этапы разработки

Этап 1. Прототип ядра и appliance-rootfs

• Buildroot: kernel с bonding, iscsi_target_mod, zfs (или lvm), squashfs, NIC/NVMe.

• Автологин в TUI-заглушку.

• Размер образа в лимите 200 МБ.

**Результат:** загружается с USB, меню «about/reboot», есть сеть.

Этап 2. Сетевая загрузка

• dnsmasq: DHCP+TFTP, iPXE BIOS/UEFI.

• LIO: один тестовый LUN (Linux или Windows image).

• Один клиент грузится diskless.

**Результат:** end-to-end PXE → iSCSI → OS.

Этап 3. Snapshot / write-back

• Пул ZFS, золотой zvol, clone на MAC.

• Политика reset при reboot.

• Super Client: promote clone → новый golden + restore point.

• Разнесение Image и Write-back.

**Результат:** два клиента с одного образа, изоляция записей; обновление образа через Super Client.

Этап 4. TUI

• Пункты раздела 5.5.

• Статус CPU/RAM/Net/Disk.

• Нет выхода в shell без пароля.

**Результат:** админ настраивает стенд без ручного редактирования конфигов.

Этап 5. Производительность

• 50+ одновременных загрузок.

• Тюнинг: irq affinity, jumbo (опционально), ARC, iSCSI queue, nic offload.

• Замер: время boot, IOPS, насыщение 10G.

**Результат:** отчёт и список параметров по умолчанию.

Этап 6 (S). Расширения

Personal/Game диски, Web UI, клиентский агент, proxyDHCP, VHDX upload с клиента.

10. Приёмка (MVP)

Система принята, если:

1. Appliance грузится с USB/DOM в TUI, bash не предлагается.

2. Из TUI настраиваются IP, DHCP-пул, роли дисков.

3. Клиент BIOS и клиент UEFI получают загрузчик и стартуют образ.

4. Два клиента на одном золотом образе не портят друг друга и не портят golden.

5. Reboot клиента в режиме Reset возвращает чистую систему.

6. Super Client сохраняет изменения в новый золотой образ; остальные видят его после своего reboot.

7. RAM-cache включается и виден в статусе (рост hit ratio или хотя бы выделенный объём ARC).

8. Write-back живёт на назначенном SSD/NVMe.

9. Размер appliance ≤ 200 МБ.

10. На стенде зафиксирован прогон ≥ 50 одновременных загрузок либо обоснованный потолок железа с планом оптимизации.

11. Документ «быстрый старт» прилагается.

4. Клиентский агент Windows: не блокирует MVP.

13. Состав поставки

• Образ USB/ISO appliance.

14. Итог

LXBoot — **Linux-appliance для diskless PXE/iSCSI**, функциональный аналог CCBoot для кафе и классов: золотой образ, write-back, Super Client, RAM+SSD cache, управление из TUI без «обычного Linux». Серверная ОС — не Windows и не полный дистрибутив, а сборка 100–200 МБ с ядром, DHCP/TFTP/iPXE, iSCSI, ZFS/LVM и оболочкой администратора.
